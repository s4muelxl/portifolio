DECISÃO DE ENGENHARIAComo manter vários domínios em uma experiência coerente?+
A escolha

Separar estado local e dados remotos: Zustand organiza a interface; TanStack Query trata consultas e sincronização.

O cuidado necessário

A separação exige fronteiras claras entre os módulos e cuidado com atualização de cache quando uma ação afeta mais de uma área.

Consultar a base técnica no GitHub ↗

Contexto e escopo

O NEXO concentra treino, rotina, refeições, finanças, investimentos e inteligência contextual em um PWA/mobile-first. O desafio é manter domínios diferentes coerentes sem transformar a interface em vários aplicativos desconectados.

Decisões de engenharia

  • Expo Router + React Native Web para compartilhar estrutura entre experiência mobile e web
  • TanStack Query para dados remotos e Zustand para estado local
  • Regras determinísticas locais antes de recorrer a providers de IA
  • Retry inteligente e fila offline para operações que podem sobreviver a perda de conexão

Segurança e dados

  • Supabase Auth, PostgreSQL e RLS nas tabelas de dados do usuário
  • Edge Functions para operações server-side
  • Credenciais privilegiadas mantidas fora do frontend
  • Web Push e Service Worker integrados ao PWA

Validação

  • Lint e TypeScript strict
  • Testes unitários com Jest
  • Typecheck e testes das Edge Functions
  • Build web reproduzível para o artefato publicado na Vercel

Escopo do case. A apresentação descreve funcionalidades e arquitetura verificáveis no repositório; não atribui métricas de uso ou impacto que não estejam medidas.

DECISÃO DE ENGENHARIAComo separar o controle da sala do transporte de mídia?+
A escolha

A aplicação organiza salas e credenciais; o LiveKit SFU distribui voz e compartilhamento de tela entre participantes.

O cuidado necessário

A mídia tem um ciclo de vida próprio. Reconexão, encerramento de tracks e leitura de qualidade precisam acompanhar mudanças da rede.

Consultar a base técnica no GitHub ↗

Contexto e problema

Plataforma privada para grupos de amigos com voz e compartilhamento de tela. O problema central é manter uma experiência simples enquanto conexão, mídia e qualidade mudam em tempo real.

Desafio técnico

  • WebRTC com ICE/STUN/TURN e codec Opus
  • SFU LiveKit para distribuição de mídia
  • Simulcast para múltiplas camadas de qualidade
  • Reconexão com backoff, jitter e leitura de RTT

Decisões de produto

  • Salas temporárias e hierarquia OWNER / ADMIN / MEMBER
  • Canais de voz dinâmicos
  • Controles de mute, deafen e dispositivos
  • Interfaces distintas para desktop e mobile quando a ergonomia exige

Validação

  • Vitest para testes unitários
  • Validação de typecheck, lint e build
  • Simulações documentadas de 30 usuários e múltiplos compartilhamentos
  • Monitoramento de FPS, memória, RTT e estados de reconexão na implementação

Escopo do case. Simulações de carga são apresentadas como simulações; metas de latência e qualidade não são tratadas como resultado de produção sem medição correspondente.

DECISÃO DE ENGENHARIAComo levar o interesse do visitante até uma proposta?+
A escolha

Manter a apresentação no frontend e concentrar geração de PDF e entrega de e-mail no backend Python/Flask.

O cuidado necessário

A entrega depende de serviços externos. Uma rota alternativa de e-mail reduz a dependência de um único provedor.

Consultar a base técnica no GitHub ↗

Contexto e problema

Site institucional e fluxo de captação de leads para uma empresa real de pisos industriais. A solução precisava apresentar serviços e obras e levar o visitante de interesse a orçamento sem uma stack pesada no cliente.

Decisões de engenharia

  • HTML, CSS e JavaScript vanilla no frontend
  • Python/Flask em funções serverless no backend
  • Propostas em PDF geradas no servidor
  • i18n pt-BR / en-US com preferência persistida

Resiliência e segurança

  • Resend como rota principal de e-mail com fallback SMTP
  • Sanitização de entradas e rate limiting
  • CSP, HSTS, X-Frame-Options e outros cabeçalhos de proteção
  • Área administrativa protegida por token

Validação e escopo

  • Fluxo comercial integra formulário, PDF e WhatsApp
  • SEO e semântica fazem parte da implementação
  • Dados demonstrativos são anonimizados
  • O repositório é publicado com autorização para portfólio

Escopo do case. O portfólio demonstra a implementação técnica; resultados comerciais e métricas de conversão não são inferidos sem dados medidos.

HTML5 · CSS3 · JavaScript · Python · Flask · Redis · Vercel

Recursos

DECISÃO DE ENGENHARIAComo reduzir cálculos e formatação feitos à mão?+
A escolha

Validar entradas, calcular subtotais e construir o recibo em UTF-8 usando a biblioteca padrão do Python.

O cuidado necessário

A execução local simplifica a instalação e o armazenamento. A demonstração deste portfólio adapta a interação ao navegador, sem executar Python no cliente.

Consultar a base técnica no GitHub ↗

Problema

Reduzir erros de cálculo e tempo gasto formatando comprovantes e recibos manualmente em vendas feitas por WhatsApp, redes sociais ou atendimento direto.

Recursos

  • Itens, quantidades e valores unitários dinâmicos
  • Subtotais e total em formato monetário brasileiro
  • Validação de vírgula/ponto e bloqueio de entradas inválidas
  • Timestamp e identificador único por recibo

Implementação

  • Python 3.8+ sem bibliotecas externas
  • Arquivos .txt UTF-8 na pasta recibos/
  • Execução pelo terminal ou executar.bat no Windows
  • Módulos nativos datetime, os e sys
Python 3 · datetime · os · sys · CLI · UTF-8
